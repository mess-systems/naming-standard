# Стандарт именования mess.systems

Стандарт именования **mess.systems**: единая грамматика для DNS-имён, хостов, репозиториев, образов, бакетов, баз данных, объектов Kubernetes, наблюдаемости, путей секретов и идентичностей (люди, администраторы, сервисные учётные записи, ИИ-агенты, рабочие нагрузки).

Это живой шаблон: его применяют, подвергают сомнению и пересматривают по мере углубления понимания. Используйте его как есть или адаптируйте под свою организацию.

**Статус:** v2, развивается. Имена и правила ещё могут меняться; изменения фиксируются в журнале изменений ниже.

## Зачем

Имена — самое дешёвое архитектурное решение и самое дорогое для изменения. Когда каждая команда называет всё по-своему, в DNS появляются названия продуктов, правила доступа прячутся в именах хостов, секреты группируются по вендорам, а сервисные учётные записи невозможно отличить от ИИ-агентов. Этот стандарт выводит каждое имя из одних и тех же немногих осей, взятых по порядку: **плоскость (plane), домен (domain), возможность (capability), продукт (product), окружение (env)**. Поэтому имя можно предсказать по исходным данным и проверить автоматически.

## Основные идеи на одном экране

- **Две грамматики DNS, третьей нет.** Внутренняя: `<capability>.<domain>.<plane>[.<env>].svc.<company-domain>`. Публичная: `<surface>.<product-domain>`. Самая левая метка — это возможность, а не продукт.
- **Одна установка, одно имя.** Псевдонимы — это редиректы с ограниченным сроком жизни.
- **Имена не несут авторизации.** Метки маршрутизируют и идентифицируют; доступ определяется группами и политиками (принцип минимальных привилегий, [NIST SP 800-53 AC-6](https://csrc.nist.gov/projects/cprt/catalog#/cprt/framework/version/SP_800_53_5_2_0/home?element=AC-06)).
- **Везде одни и те же десять ключей метаданных** (`plane, domain, capability, product, env, owner, tier, scope, data_class, exposure`). DNS кодирует четыре из них; остальные хранятся в каталогах, метаданных секретов, метках k8s и тегах гипервизора.
- **Вид идентичности виден в ID.** Агенты — не сервисные учётные записи: они действуют автономно, им нужен ответственный человек-оператор, у них собственный префикс и собственный узел секретов.
- **Секреты хранятся у своего потребителя**: одна точка монтирования на плоскость, путь `<domain>/<capability>/<env>/<item>`, политика на каждую идентичность-потребителя.
- **Три префикса групп**: `tier-`, `role-`, `app-`.
- **Домен доверия не совпадает с зоной DNS** ([SPIFFE](https://spiffe.io/docs/latest/spiffe-about/overview/)).
- **Строчные буквы, цифры, дефис** в каждом внешнем идентификаторе; `snake_case` — только там, где система запрещает дефисы.
- **Независимость от продуктов.** Продукты в примерах (IdP, менеджер секретов, mesh VPN, git-платформа, реестр, дашборды…) — взаимозаменяемые иллюстрации, а не требования.

`mess.systems` — собственный домен организации, он используется в примерах; при адаптации замените его своим.

## Обоснование решений

Стандарт сверен с DNS-ограничениями [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035), [RFC 1123](https://www.rfc-editor.org/rfc/rfc1123) и [RFC 8499](https://www.rfc-editor.org/rfc/rfc8499), а также с распространённой корпоративной практикой: [правилами именования ресурсов Microsoft Cloud Adoption Framework](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/azure-best-practices/resource-naming), рекомендациями по политикам и путям [OpenBao](https://openbao.org/docs/concepts/policies/) и [Vault](https://developer.hashicorp.com/vault/docs/concepts/policies), [спецификацией SPIFFE ID](https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE-ID.md), [правилами именования объектов Kubernetes](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) и контролями [NIST SP 800-53](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) [AC-2](https://csrc.nist.gov/projects/cprt/catalog#/cprt/framework/version/SP_800_53_5_2_0/home?element=AC-02) (управление учётными записями) и [AC-6](https://csrc.nist.gov/projects/cprt/catalog#/cprt/framework/version/SP_800_53_5_2_0/home?element=AC-06) (минимальные привилегии).

Поставлено под сомнение и сохранено:

| Вопрос | Решение | Почему |
|---|---|---|
| Шесть меток в prod (`sso.iam.shared.svc.mess.systems`) — слишком глубоко? | Сохранить | RFC 1035 допускает 63 символа на метку и 253 на имя. При выпуске ACME-сертификата на каждое имя глубина wildcard важна только для конечных точек без ACME. Глубина даёт выводимое имя |
| `svc` конфликтует с Kubernetes `svc.cluster.local`? | Сохранить `svc` | Другой суффикс, другой резолвер (см. [грамматику A](i18n/ru/01-naming-conventions.md#31-грамматика-a-внутренняя)) |
| Частный псевдо-TLD (`.lan`, `.corp`, `.internal`)? | Нет, использовать поддомен зарегистрированного домена | Публичные УЦ не выпускают на него сертификаты. `.local` зарезервирован для mDNS ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762)), не использовать никогда |
| Окружение опускается в prod DNS, но присутствует в хостах и схемах? | Сохранить | DNS сокращается по зоне; инвентарные реестры — нет |
| Общий LLM-шлюз сохраняет одно имя (`gateway.ai.corp`), даже когда им пользуются продукты? | Сохранить | Одна установка, одно имя; `gateway.ai.platform` зарезервировано, но не выпускается |

## Журнал изменений

### v2 (текущая)

- Многословные коды пишутся через дефис (`data-catalog`, `hub-cache`, `service-desk`), никогда слитно.
- Коды возможностей уникальны во **всех** доменах (например, документная БД — `docstore`, а не `docs`; трассировка LLM — `llm-traces`, а не `traces`; ИИ-ограничитель (guardrail) — `guard`, а не `policy`).
- Публичная зона `apps.<brand>` определена как зона `ext` в грамматике B.
- Форма хоста получила ведущий код площадки: `<site>-<plane>-<domain>-<product>-<env>-<NN>`.
- Добавлены соглашения о [секретах](i18n/ru/03-secrets-conventions.md) и [идентичностях](i18n/ru/04-identity-conventions.md); один набор меток метаданных применяется везде.
- Домен доверия SPIFFE — это организация (`spiffe://mess.systems`), путь `/<plane>/<domain>/<capability>`.
- Явное правило: метка DNS никогда не является входными данными для авторизации.

### v1

- Внутренняя грамматика «сначала возможность», неглубокая публичная грамматика, плоскость как первая ось изоляции, одна установка с одним URL, провайдеры как ID каталога.

## Открытые вопросы

- Типовой ранбук переключения (порядок для DNS, точек монтирования секретов, домена доверия SPIFFE). Его набросок — [порядок переключения](i18n/ru/02-worked-example.md#8-порядок-переключения) в разобранном примере.
- Останется ли `obs` отдельным доменом или войдёт в `infra`.

## Обсуждение и участие

- **Вопросы, идеи, «как бы вы назвали X?»**: начните тему в [GitHub Discussions](https://github.com/mess-systems/naming-standard/discussions).
- **Конкретные предложения изменений** (новый код, изменение правила, ошибка в примере): откройте [issue](https://github.com/mess-systems/naming-standard/issues) по шаблону *Proposal*, затем pull request.
- Сначала прочитайте [CONTRIBUTING.md](i18n/ru/CONTRIBUTING.md), особенно чек-лист перед публикацией: никогда не публикуйте реальные внутренние имена хостов, IP-адреса, секреты или персональные данные в issues, обсуждениях или примерах.

## Переводы

- Нормативным является английский текст; при любых расхождениях преимущество имеет английская версия.
- Переводы лежат в `i18n/<lang>/` под теми же именами файлов: русский — в `i18n/ru/`, упрощённый китайский — в `i18n/zh-CN/`. Переведённые README — `README.ru.md` и `README.zh-CN.md` в корне репозитория.
