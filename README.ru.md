# Стандарт именования mess.systems

Стандарт именования **mess.systems**: единая грамматика для DNS-имён, хостов, репозиториев, образов, бакетов, баз данных, объектов Kubernetes, наблюдаемости, путей секретов и идентичностей (люди, администраторы, сервисные учётные записи, ИИ-агенты, рабочие нагрузки).

Это живой шаблон: его применяют, подвергают сомнению и пересматривают по мере углубления понимания. Используйте его как есть или адаптируйте под свою организацию.

**Статус:** v2, развивается. Имена и правила ещё могут меняться; изменения фиксируются в журнале изменений ниже.

## Зачем

Имена — самое дешёвое архитектурное решение и самое дорогое для изменения. Когда каждая команда называет всё по-своему, в DNS появляются названия продуктов, правила доступа прячутся в именах хостов, секреты группируются по вендорам, а сервисные учётные записи невозможно отличить от ИИ-агентов. Этот стандарт выводит каждое имя из одних и тех же немногих осей — **плоскость (plane) → домен (domain) → возможность (capability) → продукт (product) → окружение (env)**, — так что имя можно предсказать по исходным данным и проверить автоматически.

## Основные идеи на одном экране

- **Две грамматики DNS, третьей нет.** Внутренняя: `<capability>.<domain>.<plane>[.<env>].svc.<company-domain>`. Публичная: `<surface>.<product-domain>`. Самая левая метка — это возможность, а не продукт.
- **Одна установка → одно имя.** Псевдонимы — это редиректы с ограниченным сроком жизни.
- **Имена не несут авторизации.** Метки маршрутизируют и идентифицируют; доступ определяется группами и политиками (NIST AC-6).
- **Везде одни и те же десять ключей метаданных** (`plane, domain, capability, product, env, owner, tier, scope, data_class, exposure`). DNS кодирует четыре из них; остальные хранятся в каталогах, метаданных секретов, метках k8s и тегах гипервизора.
- **Вид идентичности виден в ID.** Агенты — не сервисные учётные записи: они действуют автономно, им нужен ответственный человек-оператор, у них собственный префикс и собственный узел секретов.
- **Секреты хранятся у своего потребителя**: одна точка монтирования на плоскость, путь `<domain>/<capability>/<env>/<item>`, политика на каждую идентичность-потребителя.
- **Три префикса групп**: `tier-`, `role-`, `app-`.
- **Домен доверия ≠ зона DNS** (SPIFFE).
- **Строчные буквы, цифры, дефис** в каждом внешнем идентификаторе; `snake_case` — только там, где система запрещает дефисы.
- **Независимость от продуктов.** Продукты в примерах (IdP, менеджер секретов, mesh VPN, git-платформа, реестр, дашборды…) — взаимозаменяемые иллюстрации, а не требования.

`mess.systems` — собственный домен организации, он используется в примерах; при адаптации замените его своим.

## Обоснование решений

Стандарт сверен с ограничениями RFC 1035/1123/8499 и распространённой корпоративной практикой: правилами именования ресурсов Microsoft Cloud Adoption Framework, рекомендациями по путям Vault/OpenBao, спецификацией SPIFFE, правилами именования Kubernetes, NIST SP 800-53 AC-2/AC-6.

Поставлено под сомнение и сохранено:

| Вопрос | Решение | Почему |
|---|---|---|
| Шесть меток в prod (`sso.iam.shared.svc.mess.systems`) — слишком глубоко? | Сохранить | Лимиты RFC — 63 символа на метку, 253 всего. При выпуске ACME-сертификата на каждое имя глубина wildcard важна только для конечных точек без ACME. Глубина даёт выводимое имя |
| `svc` конфликтует с Kubernetes `svc.cluster.local`? | Сохранить `svc` | Другой суффикс, другой резолвер (01 §3.1) |
| Частный псевдо-TLD (`.lan`, `.corp`, `.internal`)? | Нет — использовать поддомен зарегистрированного домена | На него нельзя получить сертификаты публичного УЦ. `.local` — это mDNS (RFC 6762), не использовать никогда |
| Окружение опускается в prod DNS, но присутствует в хостах и схемах? | Сохранить | DNS сокращается по зоне; инвентарные реестры — нет |
| Общий LLM-шлюз сохраняет одно имя (`gateway.ai.corp`), даже когда им пользуются продукты? | Сохранить | Одна установка → одно имя; `gateway.ai.platform` зарезервировано, но не выпускается |

## Журнал изменений

### v2 (текущая)

- Многословные коды пишутся через дефис (`data-catalog`, `hub-cache`, `service-desk`), никогда слитно.
- Коды возможностей уникальны во **всех** доменах (например, документная БД — `docstore`, а не `docs`; трассировка LLM — `llm-traces`, а не `traces`; ИИ-ограничитель (guardrail) — `guard`, а не `policy`).
- Публичная зона `apps.<brand>` определена как зона `ext` в грамматике B.
- Форма хоста получила ведущий код площадки: `<site>-<plane>-<domain>-<product>-<env>-<NN>`.
- Добавлены соглашения о секретах (03) и идентичностях (04); один набор меток метаданных применяется везде.
- Домен доверия SPIFFE — это организация (`spiffe://mess.systems`), путь `/<plane>/<domain>/<capability>`.
- Явное правило: метка DNS никогда не является входными данными для авторизации.

### v1

- Внутренняя грамматика «сначала возможность», неглубокая публичная грамматика, плоскость как первая ось изоляции, одна установка → один URL, провайдеры как ID каталога.
