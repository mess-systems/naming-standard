# 07. Развёртывание и арендаторы

> Перевод носит информативный характер; нормативный текст: [английский](../../07-deployment-and-tenants.md).

Правила **продуктового контура**: облачные (cloud-native) продукты, которые mess.systems разрабатывает, эксплуатирует и продаёт, их развёртывание по провайдерам, регионам и ячейкам, и идентификация арендаторов (tenants). Все примеры используют вымышленную компанию mess.systems и её вымышленный **продукт X** (`x`): простое приложение для записей со входом, подпиской, админ-консолью, API с вебхуками и платежами.

Эта часть сложилась по итогам внешнего ревью стандарта; спасибо рецензенту.

## 1. Два контура

У mess.systems два контура. Общие у них правила символов, правило «имена не дают доступа», порядок «сначала каталог», соглашения о секретах и идентичностях и грамматика меток из [05](05-labels-and-tags.md). Различается то, из чего собирается имя.

| | Корпоративный контур | Продуктовый контур |
|---|---|---|
| Что охватывает | Внутренние сервисы, плоскости `corp`, `eng`, `shared` и `ext`, устройства сотрудников | Продукты для клиентов, их окружения, ячейки и арендаторов |
| Правила | с [01](01-naming-conventions.md) по [06](06-endpoint-conventions.md), без изменений | Эта часть поверх общих правил |
| Логическая идентичность | `<capability>.<domain>.<plane>` | `<service>.<domain>.<product>` |
| Уникальность левого кода | Код возможности уникален во всей компании | Сервис уникален внутри своего продукта |
| Внутренний DNS, prod | env опускается: `git.sdlc.eng.svc.mess.systems` | env пишется всегда: `store.records.x.prd.svc.mess.systems` |
| Публичный DNS | `www.mess.systems`, `<capability>.apps.mess.systems` | `api.<product-domain>`, `api.stg.<product-domain>` |
| Ось затрат | `capability` | `product`, `domain`, `service` |
| Домен доверия SPIFFE | `mess.systems`, non-prod `<env>.mess.systems` | `product.mess.systems`, `nonprod.product.mess.systems`, `sandbox.product.mess.systems` |

**Как они сосуществуют.**

- Объект принадлежит ровно одному контуру. Каталог записывает `contour: corp` или `contour: product`.
- Продукт уже является плоскостью в корпоративном контуре ([раздел 4.1 в 01](01-naming-conventions.md): `<product>`). Продуктовый контур это сохраняет: третья метка внутреннего имени продукта это код продукта, и он никогда не равен `shared`, `corp`, `eng` или `ext`.
- Общие сервисы всех продуктов (сборка, реестр, наблюдаемость на стороне продуктов) это продукт **`platform`**, с тем же кодом и смыслом, что и плоскость `platform`.
- Продукт пользуется корпоративными сервисами (SSO для сотрудников, git-сервер, менеджер секретов) под их корпоративными именами. Корпоративный сервис никогда не получает имя продуктового контура.
- Асимметрия окружений намеренная: корпоративный контур сохраняет короткие имена в prod; продуктовый пишет `prd`, чтобы любое имя разбиралось одинаково в любом окружении.

## 2. Продукт, домен, сервис, реализация

| Понятие | Значение | Пример продукта X |
|---|---|---|
| `product` | То, что покупает клиент | `x` |
| `domain` | Ограниченная область внутри продукта | `records`, `access`, `billing`, `integration`, `admin` |
| `service` | Устойчивый логический сервис; переживает свою реализацию | `store`, `export`, `login`, `session`, `subscription`, `payment`, `webhook`, `console` |
| `component` | Условный: отдельные развёртываемые части одного сервиса | `api`, `worker`, `migrate` |
| `implementation` | Заменяемая технология; это учёт, а не часть имени | `postgresql`, `keycloak` |

- Код сервиса уникален **внутри своего продукта**, а не во всей компании. И у `x`, и у другого продукта может быть `login`.
- Код домена может совпадать с корпоративным кодом домена только при том же смысле (`iam` означает идентичность в обоих контурах). Иначе он локален для продукта.
- Реализация это метаданные (ключ `implementation`): не DNS-метка, не сегмент пути SPIFFE и не имя сервиса в OTel. Замена PostgreSQL не переименовывает `store`.

Продукт X, полный список сервисов:

| Домен | Сервисы |
|---|---|
| `records` | `store`, `export` |
| `access` | `login`, `session` |
| `billing` | `subscription`, `payment` |
| `integration` | `webhook` |
| `admin` | `console` |

## 3. Окружения и DNS

| Окружение | Код | Контур |
|---|---|---|
| продуктивное | `prd` | оба |
| предпродуктивное | `stg` | оба |
| тестовое | `tst` | оба |
| разработка | `dev` | оба |
| песочница | `sbx` | только продуктовый: короткоживущее, без данных клиентов, свой домен доверия |

Внутренние имена продуктового контура:

```
<service>.<domain>.<product>.<env>.svc.mess.systems            # product-wide
<service>.<domain>.<cell>.<product>.<env>.svc.mess.systems     # cell-bound
```

- `store.records.x.prd.svc.mess.systems`, `store.records.c01.x.prd.svc.mess.systems`, `login.access.x.stg.svc.mess.systems`.
- `prd` пишется всегда. Корпоративное правило «в prod окружение опускается» ([раздел 3.1 в 01](01-naming-conventions.md)) не меняется и здесь не применяется.
- Компонент, которому нужно своё имя, добавляется к метке сервиса: `store-worker.records.x.prd.svc.mess.systems`.

Публичные имена остаются чистыми:

```
api.<product-domain>                 # production
api.stg.<product-domain>             # non-production surface
app.<product-domain>, docs.<product-domain>, status.<product-domain>
```

Для продукта X с условным доменом `x.example`: `api.x.example`, `app.x.example`, `api.stg.x.example`. В публичных именах нет домена, сервиса, ячейки, региона, провайдера и арендатора. Направить запрос в ячейку это задача слоя маршрутизации, а не публичного имени.

## 4. Ключи развёртывания

| Ключ | Значение | Значения | В именах |
|---|---|---|---|
| `provider` | Где работает | коды каталога; собственная инфраструктура и частное облако это значение `own`; публичные провайдеры получают нейтральные коды (`pub-a`, `pub-b`) | никогда |
| `jurisdiction` | Правовая область, правила которой действуют | непрозрачные коды каталога (`jur-a`, `jur-b`) | никогда |
| `region` | Код региона компании, в каталоге сопоставлен с регионами провайдеров | `reg-a1`, `reg-b1` | никогда |
| `site` | Физическое место или место у провайдера ([раздел 4.4 в 01](01-naming-conventions.md)) | `dc1`, `cld` | никогда в именах продуктового контура |
| `cell` | Независимо развёртываемая копия продукта, обслуживающая набор арендаторов | общие от `c01` до `c99`; выделенные `d<tenant-key>` | да, единственный ключ развёртывания в именах |
| `tenant-scope` | Как арендаторы делят ячейку | `pooled`, `dedicated` | никогда |

**Независимость от провайдера.**

- Ни одно имя не содержит провайдера. Ячейка переезжает с `own` на `pub-a` без переименования сервисов.
- Ресурсы конкретного провайдера (аккаунты, проекты, группы ресурсов, бакеты) строятся из метаданных по форме и ограничениям этого провайдера; логическая идентичность одинакова у всех провайдеров.
- Каждый продукт сохраняет возможность работать как минимум у двух провайдеров, одним из которых может быть `own`. Решение, работающее только у одного провайдера, оформляется как исключение с датой пересмотра.
- Коды провайдеров нейтральны: коммерческое название провайдера хранится в каталоге, а не в кодах, именах или метках.

## 5. Арендаторы

Арендатор определяется тремя непрозрачными ключами, снаружи внутрь:

| Ключ | Кто | Форма | Пример |
|---|---|---|---|
| `tenant-operator` | Сторона, которая эксплуатирует сервис для клиента: сама mess.systems или партнёр | `op-` и 6 символов | `op-a7k2mz` |
| `tenant-entity` | Юридическое лицо, заключившее договор | `le-` и 6 символов | `le-q4w9np` |
| `tenant-customer` | Организация конечного клиента, которая пользуется продуктом | `ec-` и 6 символов | `ec-h3t8rd` |

- 6 символов берутся из алфавита asset-id части [06](06-endpoint-conventions.md): `a-z 2-9` без `o l i`, первый символ буква. Ключи выдаёт каталог, они непрозрачны и неизменяемы. В них никогда нет названия клиента, бренда, страны или номера договора.
- Полный путь арендатора: `op-a7k2mz/le-q4w9np/ec-h3t8rd`. Если партнёра нет, оператор это mess.systems.
- В примерах и документации только обобщённые названия («оператор A», «юрлицо B», «клиент C»).
- **Арендаторы в общих ячейках никогда не попадают в имена.** Это строки данных и метки.
- **Выделенный арендатор** получает свою ячейку `d<key>` по 6 символам ключа юрлица (`tenant-entity`): `dq4w9np`. Все конечные клиенты этого юрлица работают в его выделенной ячейке. Пример: `store.records.dq4w9np.x.prd.svc.mess.systems`.

## 6. Что входит в имя

| Входит в имена | Только в метаданных |
|---|---|
| `service`, `domain`, `product`, `env`, `cell` (включая ключ выделенного арендатора) | `provider`, `jurisdiction`, `region`, `site`, `tenant-scope`, `residency`, ключи арендаторов общих ячеек, `implementation`, `owner`, `cost-center`, `criticality`, `data-class` |

## 7. Метки управления

Метки следуют грамматике [05](05-labels-and-tags.md). У каждого ключа есть класс:

- **обязательный**: задаёт автор; ресурс без него не проходит проверку.
- **условный**: обязателен, когда выполнено его условие.
- **производный**: заполняется инструментами из каталога или конвейера; вручную не вводится.

| Ключ | Класс | Значения | Примечание |
|---|---|---|---|
| `contour` | обязательный | `corp`, `product` | |
| `product`, `domain`, `service` | обязательный (продуктовый контур) | коды каталога | ось затрат продуктового контура |
| `component` | условный: у сервиса больше одной развёртываемой части | `api`, `worker`, `migrate` | |
| `env` | обязательный | `prd`, `stg`, `tst`, `dev`, `sbx` | |
| `owner` | обязательный | ID группы | как в 05 |
| `cost-center` | обязательный | `cc-<name>` | как в 05 |
| `criticality` | обязательный (продуктовый контур) | `critical`, `high`, `medium`, `low` | |
| `data-class` | обязательный | `public`, `internal`, `confidential`, `restricted` | как в 05 |
| `residency` | обязательный (продуктовый контур) | код юрисдикции или `any` | обязателен, даже если `any` |
| `tenant-scope` | обязательный (среда выполнения продуктового контура) | `pooled`, `dedicated` | |
| `cell` | условный: ресурс привязан к ячейке | `c01`, `d<key>` | |
| `tenant-operator`, `tenant-entity`, `tenant-customer` | условный: выделенный ресурс | `op-…`, `le-…`, `ec-…` | |
| `lifecycle` | условный: ресурс не обычный долгоживущий | `ephemeral`, `retiring` | отсутствие означает active |
| `provider`, `region`, `jurisdiction`, `site` | производный | из ячейки в каталоге | |
| `managed-by` | производный | `opentofu`, `argo-cd`, `ansible` | ставит модуль IaC или инструмент GitOps |
| `source-repo` | производный | `<org>/<repo>` | ставит CI |
| `implementation` | производный | код установки | из каталога |

**Согласование с 05.** Теги затрат из [раздела 2 в 05](05-labels-and-tags.md) не меняются для корпоративного контура. В продуктовом контуре обязательные теги затрат: `cost-center`, `owner`, `env`, `product`, `domain`, `service`; `capability` не ставится. `initiative` и `plane` остаются необязательными в обоих контурах.

## 8. OpenTelemetry

| Атрибут | Продуктовый контур | Пример продукта X |
|---|---|---|
| `service.namespace` | `<product>.<domain>` | `x.records` |
| `service.name` | `<service>` или `<service>-<component>` | `store`, `store-worker` |
| `deployment.environment.name` | код окружения | `prd` |
| `service.instance.id` | генерируется для каждого экземпляра | |
| `service.version` | версия релиза | |

Ячейка, режим аренды и провайдер это атрибуты ресурса с префиксом `mess.systems.` (`mess.systems.cell`), а не часть имени сервиса. Корпоративный контур сохраняет форму приложения из [раздела 5 в 01](01-naming-conventions.md).

## 9. SPIFFE

У продуктового контура три домена доверия, отдельные от корпоративного `mess.systems`:

| Домен доверия | Окружения |
|---|---|
| `spiffe://product.mess.systems` | `prd` |
| `spiffe://nonprod.product.mess.systems` | `stg`, `tst`, `dev` |
| `spiffe://sandbox.product.mess.systems` | `sbx` |

Путь: `/<product>/<domain>/<service>[/<cell>]`, в доменах non-prod и sandbox первым сегментом идёт окружение: `spiffe://product.mess.systems/x/records/store/c01`, `spiffe://nonprod.product.mess.systems/stg/x/access/login`. Переход между доменами доверия требует явной федерации; нагрузка non-prod никогда не получает продуктивную идентичность.

## 10. Исполняемый стандарт

Словарь и правила этой части также лежат в репозитории как данные:

| Путь | Содержимое |
|---|---|
| `schema/resource-metadata.schema.json` | JSON Schema метаданных ресурса продуктового контура |
| `catalog/*.yaml` | Словарь: контуры, окружения, провайдеры, юрисдикции, регионы, ячейки, домены и сервисы продукта X, классы меток |
| `tests/golden/*.yaml` | Эталонные примеры: метаданные и имена, которые из них должны получиться |
| `tests/check_golden.py` | Тест, проверяющий эталонные примеры по схеме и каталогу |

CI запускает тест в каждом pull request. Файлы данных это примеры для вымышленного продукта X; организация заменяет каталог своим.
