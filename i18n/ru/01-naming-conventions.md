# Соглашения об именовании mess.systems (v2)

> **Статус:** v2, развивается. Самодостаточен: все правила, необходимые для применения, находятся в этом репозитории.
> **Область действия:** любой идентификатор, который читает человек или машина: DNS, хосты, репозитории, образы, бакеты, базы данных, Kubernetes, наблюдаемость, ID каталога. Секреты описаны в [соглашениях о секретах](03-secrets-conventions.md), идентичности — в [соглашениях об идентичностях](04-identity-conventions.md), а полная миграция — в [разобранном примере](02-worked-example.md).
> **Домен организации:** `mess.systems` — собственный домен организации, он используется во всём документе. При адаптации стандарта подставьте свой зарегистрированный домен.

## 1. Правила для символов (действуют для всех семейств)

| Правило | Значение | Почему |
|---|---|---|
| Алфавит | `a-z 0-9 -` | имена хостов по [RFC 1123](https://www.rfc-editor.org/rfc/rfc1123), [имена Kubernetes](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/), S3, реестры контейнеров, большинство IdP |
| Регистр | только строчные | DNS нечувствителен к регистру; всё остальное — чувствительно |
| Разделитель между осями | `-` в именах, `.` в DNS и ID с точками, `/` в путях | у каждого разделителя одно значение |
| Многословный токен | через дефис (`data-catalog`), никогда слитно и не в camelCase | читаемость; DNS это допускает |
| `_` | только там, где `-` недопустим: идентификаторы SQL, переменные окружения, имена полей секретов | вынуждено системой |
| Длина метки | ≤ 63 символов; FQDN ≤ 253 | [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035) |
| `-` в начале или в конце | никогда | RFC 1123 |
| Цифры | разрешены; токен никогда не начинается с цифры | значения меток k8s, shell |
| Порядковые номера | две цифры с ведущим нулём (`01`) | правильная сортировка |
| Зарезервированные слова | `api`, `www`, `app`, `admin`, `internal`, `public`, `prod`, `test`, `svc`, `local`, `cluster` — никогда не используются как код плоскости, домена, возможности или продукта | конфликтуют с токенами грамматики или с именами, зарезервированными [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762) и [RFC 6761](https://www.rfc-editor.org/rfc/rfc6761) |

### 1.1 Правило разбора дефиса

Дефис разделяет оси имени и одновременно соединяет слова одного токена (`data-catalog`). Имя разбирается по позициям, поэтому у `dc1-eng-sdlc-data-catalog-prd-01` ровно одно прочтение.

| Правило | Значение |
|---|---|
| Коды плоскости и домена | один токен без дефиса (`shared`, `eng`, `sdlc`, `obs`) |
| Разбор | слева направо по позициям формы из [форм объектов](#5-формы-объектов): сначала площадка (только в именах хостов), затем плоскость, затем домен, затем продукт или возможность, затем окружение и порядковый номер, если они есть в форме |
| Окружение | всегда код из [окружений и площадок](#44-окружения-и-площадки), поэтому распознаётся по значению |
| Порядковый номер | всегда две цифры на последней позиции |
| Остаток | всё между доменом и окружением (или концом имени) — один токен продукта или возможности, даже если в нём есть дефисы |
| Проверка | имя допустимо, только если каждая позиция совпадает со своим списком в `catalog/`; несовпадение — отказ, а не догадка |

Пример: `dc1-eng-sdlc-data-catalog-prd-01` — площадка `dc1`, плоскость `eng`, домен `sdlc`, продукт `data-catalog`, окружение `prd`, номер `01`.

Уточнения владельца, области и окружения никогда не входят в имя. Они живут только в метках и тегах (`owner`, `scope`, `env`, см. [метки и теги](05-labels-and-tags.md)), которые обязательны в любом случае. Двойной дефис не используется как разделитель уточнения: он конфликтует с зарезервированной формой DNS-меток `xn--` ([RFC 5891](https://www.rfc-editor.org/rfc/rfc5891)). Форма RoleBinding `<role>--<subject>` ([RBAC в Kubernetes](04-identity-conventions.md#10-rbac-в-kubernetes)) не меняется: она соединяет два полных имени и уточнением не является.

## 2. Десять ключей метаданных

Каждое семейство объектов несёт одни и те же ключи. DNS кодирует первые четыре (плюс окружение, если оно не prod). Остальные хранятся в каталоге соответствующего семейства.

| Ключ | Значения | Где кодируется |
|---|---|---|
| `plane` | `shared corp eng platform ext <product>` | DNS, хост, репозиторий, метка k8s, точка монтирования секретов |
| `domain` | [коды доменов](#42-домены) | DNS, хост, репозиторий, схема |
| `capability` | [коды возможностей](#43-коды-возможностей-уникальны-во-всех-доменах) | самая левая метка DNS, путь SPIFFE, цель MCP |
| `product` | код установки (`keycloak`, `gitea`) | хост, репозиторий, образ, пространство имён k8s |
| `env` | `prd dev tst stg` | DNS (только не prod), хост, схема, путь секрета (всегда) |
| `owner` | ID группы (см. [владельцы](04-identity-conventions.md#5-владельцы)) | каталог, метаданные секретов, метка k8s |
| `tier` | `t0 t1 t2 t3` (уровни привилегированного доступа, см. [группы уровней](04-identity-conventions.md#31-группы-уровней-привилегии)) | каталог, группа идентичностей |
| `scope` | `dev tst stg prd` — наивысшее окружение, для которого объект сертифицирован | только каталог |
| `data_class` | `public internal confidential restricted` | каталог, метаданные секретов, тег бакета |
| `exposure` | `mesh lan public` | каталог, группа mesh-сети — **никогда в имени** |

[Ключи меток Kubernetes](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/): `mess.systems/<key>`. Теги облака и гипервизора: нативные теги «ключ/значение»; `<key>-<value>` (`plane-corp`) только там, где платформа их не поддерживает. Все метки и теги следуют [Меткам и тегам](05-labels-and-tags.md). Метки реестра контейнеров: так же, как теги гипервизора. Менеджер секретов: `custom_metadata.<key>`.

Эти десять ключей описывают **корпоративный контур**. **Продуктовый контур** (продукты для клиентов, их ячейки и арендаторы) использует `product`, `domain`, `service` и `implementation`, а также ключи развёртывания и арендаторов; см. [07 Развёртывание и арендаторы](07-deployment-and-tenants.md#1-два-контура).

## 3. DNS: две грамматики и ничего больше

### 3.1 Грамматика A: внутренняя

```
<capability>.<domain>.<plane>.svc.mess.systems                 # prod
<capability>.<domain>.<plane>.<env>.svc.mess.systems           # dev|tst|stg
<surface>.<product>.svc.mess.systems                           # superseded by 07 (product contour)
```

- `svc.mess.systems` — внутренняя зона (split-horizon, внутренний УЦ + ACME). Публично не делегируется. `svc` здесь означает «зона сервисов» и не связан с Kubernetes `*.svc.cluster.local` — другой суффикс, другой резолвер.
- Самая левая метка — это **возможность (capability)**, а не продукт (`git`, а не `gitea`). Продукт — это предмет инвентаризации, а не часть имени.
- В prod окружение опускается. Во всех остальных местах (хосты, схемы, секреты) `prd` пишется.
- Продуктовый контур пишет `prd` и во внутреннем DNS; см. [07 Окружения и DNS](07-deployment-and-tenants.md#3-окружения-и-dns). Асимметрия намеренная: корпоративные имена остаются короткими, а продуктовые разбираются одинаково в любом окружении.
- Одна установка имеет ровно одно каноническое FQDN. Псевдонимы — это редиректы, а не имена.
- **Метка никогда не является входными данными для авторизации.** Доступность и права определяются группами mesh-сети, группами IdP и политиками менеджера секретов (см. [соглашения об идентичностях](04-identity-conventions.md)). Два потребителя одной установки используют одно и то же имя и разные группы.

### 3.2 Грамматика B: публичная

```
<surface>.<product-domain>            # www | app | api | docs | status | auth
<capability>.apps.mess.systems        # ext plane on the brand domain
<surface>.<product>.x.mess.systems    # products in the showcase sub-zone
www.mess.systems                      # brand
```

- Публичные имена никогда не содержат плоскость, домен, окружение или вендора. Единственное исключение — непродуктивная поверхность продукта (`api.stg.<product-domain>`, см. [окружения и DNS](07-deployment-and-tenants.md#3-окружения-и-dns)).
- У бренда ровно две публичные подзоны, третьей нет:
  - `apps.mess.systems` несёт возможности `ext` (партнёрские и демо-порталы): `<capability>.apps.mess.systems`. Это грамматика B, где в роли продукта выступает бренд.
  - `x.mess.systems` несёт продукты продуктового контура ([развёртывание и арендаторы](07-deployment-and-tenants.md)): домен продукта `<product>.x.mess.systems`, поверхности `<surface>.<product>.x.mess.systems`, непродуктивные поверхности `<surface>.<env>.<product>.x.mess.systems`. Продукт с собственным зарегистрированным доменом использует этот домен вместо подзоны, но не оба сразу.
- `x` — метка подзоны, а не код продукта и не название платформы. Набор продуктов, опубликованных в `x.mess.systems`, называется **витриной**. Метка подзоны никогда не бывает кодом продукта в каталоге организации. Вымышленного продукта `x` из примеров [развёртывания и арендаторов](07-deployment-and-tenants.md#2-продукт-домен-сервис-реализация) в этом каталоге нет; там `x.mess.systems` — условный домен продукта.
- Вершина домена продукта (`arch.x.mess.systems`) — главная поверхность продукта, как `www` для бренда.
- Публичное имя под `mess.systems` вне грамматик A и B допускается только как зафиксированное исключение в `catalog/dns-exceptions.yaml`: имя, его каноническое имя грамматики A, причина, группа-владелец и дата пересмотра. Типичный случай — «красивое» имя управляющей плоскости, которая должна быть доступна до поднятия mesh-сети, например координатора mesh. Имя вне обеих грамматик без записи отклоняется. Исключение никогда не служит шаблоном для нового имени.

```yaml
- name: netbird.mess.systems
  canonical: mesh.net.shared.svc.mess.systems
  reason: the mesh coordinator must be reachable before the mesh is up
  owner: role-platform-engineers
  review: 2027-10-31
```

### 3.3 Грамматики C не существует

| Распространённый антипаттерн | Почему это не имя | Целевое состояние |
|---|---|---|
| `*.admin.corp.lan`, `*.private.corp.lan` | уровень доступности (exposure) в имени | то же FQDN, другая группа mesh/IdP |
| `*.mesh`, `*.apps.mesh` | псевдо-TLD внутри mesh; не разрешается за пределами DNS mesh-сети | грамматика A |
| `vcenter.corp.lan` (продукт, а не возможность) | нарушает правило «слева — возможность» | `compute.infra.shared.svc.mess.systems` |
| имена папок репозитория (`infra/llm-proxy`) | папка репозитория — не ось именования | `gateway.ai.corp` |

## 4. Коды

### 4.1 Плоскости

| Код | Потребитель | Доверие |
|---|---|---|
| `shared` | управляющие плоскости, от которых зависят все (IAM, PKI, секреты, DNS, mesh, наблюдаемость, гипервизор) | наивысшее |
| `corp` | сотрудники | внутреннее |
| `eng` | инженеры, создающие продукты | внутреннее |
| `platform` | среда выполнения, общая для продуктов | продуктовое |
| `<product>` | собственная среда выполнения одного продукта | продуктовое |
| `ext` | партнёры, демо, публичные порталы | внешнее |

### 4.2 Домены

| Код | Домен | Плоскость по умолчанию |
|---|---|---|
| `iam` | идентичность, доступ, PKI, секреты, пароли | shared |
| `gov` | архитектура, политики, CMDB, ADR | corp |
| `sec` | обнаружение угроз, управление уязвимостями, SIEM | shared |
| `obs` | метрики, логи, трассировки, оповещения (см. [открытые вопросы](../../README.ru.md#открытые-вопросы) в README) | shared |
| `net` | DNS, mesh, edge, межсетевой экран | shared |
| `infra` | вычисления, хранение, резервное копирование, гипервизор | shared |
| `sdlc` | код, CI, артефакты, GitOps | eng |
| `adlc` | жизненный цикл ИИ и агентов, оценки (evals), sidecar-политики | eng |
| `ai` | инференс, шлюз, речь, зрение, агенты | corp |
| `data` | хранилище данных, конвейеры, каталог, BI, документное хранилище | platform |
| `collab` | чат, вики, документы, видео | corp |
| `comm` | почта, уведомления | corp |
| `biz` | ERP/CRM/финансы | corp |
| `itsm` | служба поддержки, управление изменениями | corp |
| `api` | управление API для продуктов | platform |
| `edge` | входящий трафик (ingress) для продуктов | platform |
| `device` | устройства сотрудников, агенты на устройствах, виртуальные рабочие столы | corp |

### 4.3 Коды возможностей (уникальны во всех доменах)

Код имеет **одно значение** во всей компании. Один и тот же код может встречаться в нескольких плоскостях (`egress.net.corp`, `egress.net.platform`), поскольку плоскость — это другая ось; но он не может встречаться в двух доменах.

| Домен | Коды |
|---|---|
| `iam` | `sso directory pki spiffe secrets passwords b2b` |
| `gov` | `cmdb archrepo adr policy catalog demo audit` |
| `sec` | `siem vuln ids scan` |
| `obs` | `dashboards metrics logs traces alerts` |
| `net` | `dns mesh ingress egress firewall` |
| `infra` | `compute storage backup k8s` |
| `sdlc` | `git ci oci packages gitops flags hub-cache` |
| `adlc` | `registry sandbox evals` |
| `ai` | `gateway inference stt tts ocr llm-traces kb docs guard assistant` |
| `data` | `warehouse orchestrate transform ingest data-catalog bi docstore convert sql cache objects` |
| `collab` | `chat wiki intranet video` |
| `comm` | `mail notify` |
| `biz` | `crm billing` |
| `itsm` | `service-desk change` |
| `api` | `gateway-api portal-api` |
| `edge` | `lb` |
| `device` | `endpoint vdi` |

`endpoint` относится к стороне устройства: так называется всё, что работает на устройствах сотрудников, и этот код никогда не входит в DNS-имя; `vdi` это серверное виртуальное рабочее место, его имя строится как у любого сервиса (`vdi.device.corp.svc.mess.systems`). См. [06](06-endpoint-conventions.md#6-код-возможности-endpoint).

Эта таблица — пример эталонного набора, а не инвентарь; расширяйте или сокращайте её под свою организацию по правилу ниже.

Добавление кода: проверьте уникальность по всей таблице, многословные коды пишите через дефис, сначала зарегистрируйте возможность в каталоге возможностей, затем здесь.

### 4.4 Окружения и площадки

| Окружение | Код | Площадка | Код |
|---|---|---|---|
| продуктивное | `prd` | собственный (on-premises) ЦОД | `dc1` |
| предпродуктивное (staging) | `stg` | тенант в публичном облаке | `cld` |
| тестовое | `tst` | | |
| разработка | `dev` | | |
| песочница (только продуктовый контур, см. [07](07-deployment-and-tenants.md)) | `sbx` | | |

Коды площадок короткие и специфичны для организации; два приведённых выше — примеры. Код площадки регистрируется в `catalog/sites.yaml` до появления первого хоста на этой площадке: код (от 2 до 4 символов `a-z0-9`, начинается с буквы), вид (`own` или `cld`) и группа-владелец. Код площадки никогда не содержит город, адрес или название провайдера; провайдер — это ключ развёртывания `provider` ([ключи развёртывания](07-deployment-and-tenants.md#4-ключи-развёртывания)).

## 5. Формы объектов

| Семейство | Форма | Пример |
|---|---|---|
| Внутреннее FQDN | [грамматика A](#31-грамматика-a-внутренняя) | `git.sdlc.eng.svc.mess.systems` |
| Публичное FQDN | [грамматика B](#32-грамматика-b-публичная) | `app.shopfront.x.mess.systems` |
| Приложение (каталог, `service.name`, slug OIDC, AppRole) | `<plane>-<domain>-<product>` | `eng-sdlc-gitea` |
| Хост / контейнер / ВМ | `<site>-<plane>-<domain>-<product>-<env>-<NN>` | `dc1-eng-sdlc-gitea-prd-01` |
| Узел гипервизора | `<site>-shared-infra-<hypervisor>-<env>-<NN>` | `dc1-shared-infra-kvm-prd-01` |
| Корпоративное конечное устройство (ноутбук, настольный компьютер) | `<profile>-<form>-<asset-id>`, см. [06 Соглашения для конечных устройств](06-endpoint-conventions.md) | `std-lt-a1b2c3` |
| Git-организация / репозиторий | организация `<plane>` · репозиторий `<domain>-<product>` | `eng/sdlc-gitea` |
| Репозиторий инфраструктуры как кода, плоская организация | `<plane>-<domain>-iac` | `shared-sec-iac`, `shared-obs-iac` |
| Репозиторий инфраструктуры как кода продукта | `<product>-<domain>-iac` | `platform-build-iac`, `shopfront-edge-iac` |
| Репозиторий инфраструктуры как кода, организация на плоскость | организация `<plane>` · репозиторий `<domain>-iac` | `shared/infra-iac` |
| Общая библиотека ролей или модулей | репозиторий-владелец + `-roles` или `-modules` | `shared-infra-iac-roles` |
| Образ контейнера | `oci.sdlc.eng.svc.mess.systems/<plane>-<domain>/<product>[-<component>]:<tag>` | `oci.sdlc.eng.svc.mess.systems/corp-ai/agentgateway:1.6.0` |
| Проект реестра (например, Harbor) | `<plane>-<domain>` | `corp-ai` |
| Фид пакетов | `<ecosystem>-<plane>` или `<ecosystem>-proxy` | `npm-proxy`, `pypi-eng` |
| S3 / бакет объектного хранилища | `<plane>-<domain>-<capability>-<env>` | `platform-data-warehouse-prd` |
| База данных Postgres | `<plane>_<domain>_<capability>_<env>` | `eng_sdlc_git_prd` |
| Схема Postgres / ClickHouse | как у базы данных | `platform_data_warehouse_prd` |

| Системный отправитель почты | `<capability>@mess.systems` | `alerts@mess.systems` |

Репозитории инфраструктуры как кода: инструмент (`ansible`, `opentofu`, `terraform`) и площадка (`dc1`, `cld`, название облака) никогда не входят в имя репозитория. Они становятся папками внутри (`stacks/<site>/…`, `roles/`, `modules/`); инструмент уже записан в метке `managed-by` ([развёртывание и арендаторы](07-deployment-and-tenants.md#7-метки-управления)). Один репозиторий обслуживает одну пару плоскости и домена: две системы разных доменов на одной машине получают два репозитория, а общая машина описывается в инвентаре. Суффикс `-iac` зарезервирован за кодом инфраструктуры.

## 6. Единый базовый URL

У одной установки один базовый URL: `https://<fqdn>`. Мультиарендность на основе путей (`/admin`, `/ui`) — дело продукта; в FQDN она не отражается. Редиректы со старых имён допускаются на 90 дней и вносятся в таблицу миграции, после чего удаляются.

## 7. TLS

- Внутренний: [ACME](https://www.rfc-editor.org/rfc/rfc8555) через `pki.iam.shared`. По умолчанию сертификат выпускается на каждое имя (например, ingress-прокси с TLS по требованию). Заранее выпущенные wildcard-сертификаты — только для конечных точек, которые не умеют ACME: по одному на пару `<domain>.<plane>`, с учётом в реестре сертификатов развёртывания (пример см. в шаге [«Сертификаты»](02-worked-example.md#6-сертификаты) разобранного примера).
- Публичный: публичный УЦ через DNS-01 на домене продукта. Один wildcard на домен продукта.
- Имена в SAN — всегда каноническое FQDN плюс перечисленные редиректы, но никогда не унаследованные имена.

## 8. Провайдеры и исходящий трафик

- Внешние вендоры — это ID каталога (`<vendor>.<service>`), а не внутренние FQDN.
- Исходящий трафик к вендору идёт через возможность-владельца (`gateway.ai.corp` для LLM-провайдеров, группы egress `mesh.net.shared` для сети).
- Секреты провайдеров хранятся по пути **потребляющей** возможности (см. [элементы и поля](03-secrets-conventions.md#4-элементы-и-поля)).

## 9. Процедура именования

- **Шаг A, сбор исходных данных (intake).** Определите оси в таком порядке: плоскость, домен, возможность, продукт, окружение, затем владелец, уровень, scope, data_class и exposure.
- **Шаг B, кодирование.** Выведите FQDN ([грамматики DNS](#3-dns-две-грамматики-и-ничего-больше)), затем имена приложения и хоста ([формы объектов](#5-формы-объектов)), затем формы конкретных семейств. Зарегистрируйте имя в каталоге до создания записей DNS.
- **Шаг C, идентичности и секреты.** Создайте группы и машинную роль ([соглашения об идентичностях](04-identity-conventions.md)) и путь секрета ([соглашения о секретах](03-secrets-conventions.md)).
- **Шаг D, наблюдаемость.** Задайте `service.name` равным имени приложения, а папку дашбордов — `<plane>-<domain>`.
