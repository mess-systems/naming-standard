# Метки и теги: теги затрат, метки CI-раннеров, Kubernetes, облако, метки задач

> **Статус:** v2.1, развивается. Принято 15.10.2026. Распространяет [десять ключей метаданных](01-naming-conventions.md) на все метки и теги вида ключ/значение.
> **Независимость от продуктов.** Продукты здесь (Forgejo, GitHub, Kubernetes, Cloudflare, cloud.ru, OpenTofu) это иллюстрации; правила применяются к любой платформе с метками или тегами.
> **Метка или тег никогда не участвует в авторизации**, как и имя.

## Зачем

В только что созданной организации на собственном git-сервере не запускался ни один CI-job: workflow запрашивал метку раннера, которая была только у раннеров другой организации. По метке нельзя было понять, где раннер виден, а раннера, на который может рассчитывать любая организация, не было. Задачи молча висели в очереди. Эта часть делает область видимости явной, вводит раннер по умолчанию и применяет одну грамматику к тегам затрат, меткам Kubernetes, облачным тегам и меткам задач.

## 1. Общая грамматика

### 1.1 Символы

- Ключ: `[a-z][a-z0-9-]*`, с необязательным префиксом `<org-domain>/` там, где платформа поддерживает префиксы (Kubernetes).
- Значение: `[a-z0-9][a-z0-9-]*`: код из списков стандарта, ID из каталога или ID группы.
- Без заглавных букв, пробелов и подчёркиваний в новых ключах. `data_class` из десяти ключей в тегах пишется `data-class`: часть платформ не принимает `_` в значениях, а дефис уже разделитель стандарта.
- Токен никогда не начинается с цифры, как требует [01, раздел 1](01-naming-conventions.md).

### 1.2 Ключи

| Ключ | Значения | Источник |
|---|---|---|
| `plane` | коды plane | [01, раздел 4.1](01-naming-conventions.md) |
| `domain` | коды доменов | [01, раздел 4.2](01-naming-conventions.md) |
| `capability` | коды capability | [01, раздел 4.3](01-naming-conventions.md) |
| `product` | код установки | каталог |
| `env` | `prd stg tst dev` | [01, раздел 4.4](01-naming-conventions.md) |
| `owner` | ID группы, никогда не человек | [04, раздел 5](04-identity-conventions.md) |
| `data-class` | `public internal confidential restricted` | [01, раздел 2](01-naming-conventions.md) |
| `cost-center` | код из каталога, например `cc-platform` | раздел 2 |
| `initiative` | код из каталога, например `ini-ai-gateway` | раздел 2 |

### 1.3 Ограничения платформ

| Платформа | Ключ | Значение | Символы | Прочее |
|---|---|---|---|---|
| Метка Kubernetes | имя 63, необязательный префикс (DNS-поддомен) до 253 | 63, может быть пустым | буквы, цифры, `-`, `_`, `.`; начинается и заканчивается буквой или цифрой | аннотации: всего до 256 КиБ на объект |
| Cloudflare Resource Tagging | 256 | 1024, может быть пустым | ключ: буквы Unicode, цифры, `_`, `.`, `-`; регистр важен | бета: 10 000 тегов на аккаунт; `PUT` заменяет все теги ресурса |
| cloud.ru Tag Management Service (Advanced) | 36 | 43 | ключ: буквы, цифры, `_`, `-`; в значении ещё `.` | 10 тегов на ресурс; одно значение на ключ |
| cloud.ru Evolution | уточнить | уточнить | уточнить | открытое примечание: ограничения не подтверждены в публичной документации (проверено 15.10.2026) |
| Метка задачи/PR в Forgejo | имя, область до последнего `/` | | свободный текст | цвет обязателен; область может быть исключающей |
| Метка задачи/PR в GitHub | имя до 50 | | свободный текст | цвет обязателен |
| Метка раннера Forgejo / GitHub | короткий токен | | держать в `[a-z0-9-]` | `runs-on` сравнивает точно |

Расчётный предел берём по самому узкому месту: **ключ до 36 символов, значение до 43**. Все пары из кодов выше в него укладываются.

### 1.4 Никогда в метках и тегах

Имена и логины пользователей, адреса почты, имена хостов, IP-адреса, серийные номера, секреты и пути к секретам, группы доступа, используемые для авторизации, имена клиентов, всё о семье и детях. Список тот же, что для имён. Теги часто видит больше людей, чем сам ресурс, например в выгрузках биллинга.

## 2. Теги затрат (FinOps)

| Ключ | Обязателен | Значение | Пример |
|---|---|---|---|
| `cost-center` | да | код каталога `cc-<name>` | `cc-platform` |
| `owner` | да | ID группы | `role-platform-engineers` |
| `env` | да | код env | `prd` |
| `capability` | да | код capability | `inference` |
| `initiative` | нет | код каталога `ini-<name>` | `ini-exo-pilot` |
| `plane` | нет | код plane | `platform` |

- `owner` и `cost-center` разделены: владелец эксплуатирует ресурс, центр затрат за него платит.
- Ось затрат это `capability`, а не `product`. Расходы по capability переживают замену продукта.
- Ресурс без четырёх обязательных тегов попадает в отчёт проверки затрат, а модули IaC его не создают (модули OpenTofu проверяют теги).
- Коды `cc-*` и `ini-*` регистрируются в каталоге до использования. Значение тега, которого нет в каталоге, это ошибка.
- Общие ресурсы получают `owner` и `cost-center` платформы; распределение по потребителям делается отчётом, а не тегом.

**Продуктовый контур.** Там обязательные теги затрат: `cost-center`, `owner`, `env`, `product`, `domain`, `service`; `capability` не ставится. Полный список меток управления с классами (обязательные, условные, производные) в [07 Метки управления](07-deployment-and-tenants.md#7-метки-управления).

## 3. Метки CI-раннеров

И Forgejo Actions, и GitHub Actions выбирают раннер, сравнивая `runs-on` с метками раннеров. Раннеры регистрируются на уровне инстанса, организации или репозитория (в GitHub: enterprise, организация или репозиторий, с группами раннеров). Задача видит только раннеры своего уровня и выше.

### 3.1 Форма меток

| Метка | Смысл | Пример |
|---|---|---|
| `default` | базовый раннер для обычных задач; зарегистрирован на **уровне инстанса** и виден каждой организации | `runs-on: default` |
| `<purpose>` | назначение раннера | `docker`, `review`, `gpu`, `build`, `deploy` |
| `<purpose>-<isolation>` | назначение плюс уровень изоляции, если вариантов несколько | `docker-socketless`, `docker-sock` |
| `scope-<level>` | где зарегистрирован раннер, справочно | `scope-instance`, `scope-org`, `scope-repo` |

Коды изоляции, от самой сильной к самой слабой:

| Код | Смысл |
|---|---|
| `vm` | каждая задача в своей VM или MicroVM |
| `socketless` | контейнерные задачи без доступа к демону контейнеров хоста (rootless-сборщик) |
| `sock` | задаче доступен сокет контейнеров хоста; по сути это root на хосте раннера |
| `host` | задача выполняется прямо на хосте раннера |

### 3.2 Правила

- Каждый инстанс git-сервера ОБЯЗАН иметь хотя бы один раннер с меткой `default` на уровне инстанса. Тогда новая организация запускает CI в первый же день.
- Workflow, которому нужно больше, чем `default`, указывает метку назначения. Если такой метки нет на уровне инстанса, это написано в README workflow.
- Раннеры `sock` и `host` НЕ регистрируются на уровне инстанса, только на уровне организации или репозитория: они дают задаче контроль над хостом.
- Метки `scope-*` справочные и никогда не используются в `runs-on`; видимость определяет сам git-сервер.
- Имена раннеров (не метки) следуют форме хостов стандарта; метки никогда не содержат имён хостов.
- В Forgejo метка раннера содержит после двоеточия ещё и способ исполнения (`docker-socketless:docker://<image>`). Имя метки это только часть до двоеточия, и она следует этой грамматике.

## 4. Метки и аннотации Kubernetes

### 4.1 Метки

| Ключ | Значение | Обязательна |
|---|---|---|
| `app.kubernetes.io/name` | код продукта | да |
| `app.kubernetes.io/instance` | имя приложения из форм объектов стандарта | да |
| `app.kubernetes.io/component` | компонент | где уместно |
| `app.kubernetes.io/part-of` | код capability | да |
| `app.kubernetes.io/managed-by` | инструмент, например `argocd`, `helm` | да |
| `app.kubernetes.io/version` | версия | нет |
| `mess.systems/plane` | код plane | да |
| `mess.systems/domain` | код домена | да |
| `mess.systems/env` | код env | да |
| `mess.systems/owner` | ID группы | да |
| `mess.systems/cost-center` | `cc-*` | да |
| `mess.systems/data-class` | класс данных | где хранятся данные |

В публичном стандарте префикс `mess.systems/`. Организация, которая принимает стандарт, заменяет его своим доменом (например, `<org-domain>/`).

### 4.2 Метка или аннотация

- **Метка:** коротко, стабильно, используется в селекторах, отчётах о затратах или политиках: ключи выше.
- **Аннотация:** всё остальное: ссылки на каталог или runbook, `initiative`, описания, метаданные сборки, ID изменений, каналы связи.
- Значение, которое меняется при каждом деплое (хеш коммита, номер сборки), никогда не метка.

## 5. Облачные теги

- **Cloudflare:** нативные теги ключ/значение через Resource Tagging. Ключи из раздела 1.2 без префикса. Регистр важен, поэтому только строчные. `PUT` заменяет все теги, поэтому теги ведёт только IaC, не руками.
- **cloud.ru:** нативные теги ключ/значение. В Tag Management Service ключ до 36 символов, значение до 43, не больше 10 тегов на ресурс. Шесть ключей раздела 2 плюс `data-class` занимают 7. Ограничения Evolution пока не подтверждены (открытое примечание).
- Платформы без тегов ключ/значение используют прежнюю форму `<key>-<value>` (`env-prd`).

## 6. Метки задач и PR

### 6.1 Грамматика

`<prefix>/<value>`. Forgejo считает областью текст до последнего `/` и умеет делать область исключающей. В GitHub областей нет, поэтому имена те же, а исключающность проверяет workflow.

| Префикс | Исключающий | Цвет | Допустимые значения |
|---|---|---|---|
| `type` | да | синий `#1d76db` | `bug feature docs chore decision research` |
| `stream` | нет | зелёный `#0e8a16` | список потоков работ из каталога |
| `horizon` | да | фиолетовый `#5319e7` | `now next later` |
| `contour` | да | оранжевый `#d93f0b` | `public private` |
| `initiative` | нет | серый `#6a737d` | коды `ini-*` из каталога |

- Один цвет на префикс, чтобы префикс был виден сразу.
- Значения в той же кодировке, что в разделе 1.1.
- Значения `initiative/` это те же коды, что в теге затрат `initiative`, так что работа и расходы связываются по одному ключу.

### 6.2 Метки в старой форме

Метки в старой форме `prefix:value` (`type:bug`) переименовываются в `prefix/value` (`type/bug`). Исключающие префиксы обеспечивают scoped-метки Forgejo, а в GitHub проверка в workflow.
